# Team installation package

Build a clean shareable ZIP from the repository root:

```text
npm run package:check
npm run package:team
```

Output: `releases/SalesGod-Team-0.4.4.zip` plus its `.sha256` file. The archive contains a `SalesGod-Team` folder, `SETUP.html`/`SETUP.md`, root-level Windows/Mac launchers, runtime bootstrap scripts, the audio bridge, extension 0.4.0 and blank `.env.example`. If Node.js 24 and npm are unavailable, either Start or Configure downloads a private Node.js v24.21.0 archive from `https://nodejs.org/dist/v24.21.0/`, verifies its pinned SHA-256 from `NODE-SHASUMS256.txt`, and extracts it under this installation's ignored `.runtime` folder. The hashes were checked against the official release SHASUMS256.txt. Supported targets are win-x64, win-arm64, darwin-x64 and darwin-arm64. A suitable existing Node/npm is reused. No system installer, permanent PATH edit, execution-policy change, admin prompt or security bypass is used. Chrome installation remains a separate user/IT step.

First Start also downloads locked production libraries from npm with dependency install scripts disabled. Runtime PATH changes affect only the launcher process and its children. Windows uses built-in PowerShell/.NET for download/hash validation and Windows tar for extraction (avoiding legacy .NET ZIP long-path failures). Mac uses curl with HTTPS-only redirects, shasum and tar. Concurrent runtime setup is locked, failed downloads stop before extraction, and cached archives are rechecked. A stale Mac lock after an abrupt termination requires operator/IT review; no recursive cache deletion is automated. No Docker, VB-CABLE, registry changes, background service or firewall edits are performed. The `.command` files are executable in ZIP metadata; Mac scripts use LF independently of the builder's OS.

Only distribute the fresh ZIP produced by the allowlist builder. Never ZIP an installed folder: it can contain `.env`, contacts/transcripts, suppression databases, exports and the downloaded `.runtime` cache. Both `releases/` and `.runtime/` are ignored and never recursively packaged. Per-file SHA-256 checksums are included in the archive and an archive checksum is written alongside it; these detect accidental changes and do not constitute a publisher signature. Pinned Node release hashes are a separate check of upstream runtime archives. Review/update those pins explicitly for a new runtime release; never resolve and execute an unchecked latest download at launch.

The source launcher files here are templates copied to the archive root. Run the extracted root launchers, not these templates directly. The common launcher lives at `tools/distribution/launcher.mjs` in the installed package; it creates `.env` exclusively without replacing an existing file, checks the tested Node major and loopback port, installs libraries when the lock fingerprint changes, and runs the bridge in the terminal. Configure opens the local file in Notepad/TextEdit for the human to enter the key. The launcher never reads or prints the key. No startup action starts a calling list.

`runtime-package.json` and `runtime-package-lock.json` are a separate production-only manifest/lock snapshot of the tested Fastify dependency tree. Keep them aligned when updating runtime dependencies; npm ci from a clean extracted archive must pass. The main development lockfile is not shipped. Change the runtime package version for a new distribution release, and keep extension/setup version descriptions accurate.

Current validation on Windows: independent tar ZIP extraction, clean production npm ci, 15 package runtime routes through Fastify inject, simulation enabled by default, zero upstream API requests, and Windows launcher's occupied-port error path leaving the current bridge untouched. Both Mac scripts pass Bash syntax checking; executable ZIP metadata and line endings are covered by tests. No macOS runtime, Gatekeeper, Finder extraction, installation or telephone-audio validation has been performed. Do not describe this as a signed/notarized installer or promise Mac call compatibility.

Windows validation also hid system Node from a child process PATH: the bootstrap downloaded, checksum-verified and extracted the official Windows x64 runtime into a long folder path with spaces, then successfully ran private Node and npm. A corrupted-cache regression proves rejection before extraction. The development machine's global Node/PATH and running bridge were unchanged. Windows ARM64 and both actual Mac runtime paths still need hardware testing; shell syntax and all four pin mappings have automated coverage.

`npm run check` includes six offline distribution regressions in addition to application checks (120 total tests on Windows plus type checking as of this package; one Windows-only test skips on other systems). A real Mac smoke test and separately authorized telephone test remain necessary. The package keeps the current Jay Marketing Lab/Cena live identity and Sina voicemail; the colleague guide explicitly requires review. It provides local per-computer records, not a shared multi-user service.

Package 0.4.4 rewrites SETUP.md as numbered Windows/Mac instructions, including launch output, manual commands, mode-before-import, notifications, logs, shutdown prompts and troubleshooting. The package builder regenerates SETUP.html from this source using build-setup-guide.mjs, preserving numbered steps around command blocks. The generated guide has a contents menu and printable layout. No runtime or extension behavior changes in this release.
